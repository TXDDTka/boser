## Status
Accepted

## Date
2026-10-18

## Last Verified

## Decision Makers
Пользователь (владелец проекта); черновик — `/architecture-decision`; ревью — unity-specialist, technical-director (TD-ADR).

## Summary
Восемь с лишним систем (Оружие, Здоровье, Благословения, Прокачка у королев, Дропы/удача, Сайдгрейды, Тюрьма, Контекст забега) меняют одни и те же числа Чемпиона и подменяют эффекты (тип молитвы, тип основного оружия), что грозит превратить Модификаторы в God Object. Решено: один типизированный стек на владельца — числа по `StatId` собираются из трёх слоёв плюс override, слоты эффектов по `SlotId` разрешаются приоритетом из данных; источники видны стеку только как непрозрачные handle со сроком жизни, потребители читают значения pull-ом из кэша с версией, без событий и без аллокаций.

## Context

### Problem Statement
По `systems-index.md` от Модификаторов зависят 8+ систем, и это помечено как **узкое место** и риск God Object. Источники сил очень разные по природе: постоянная прокачка (Альмиэль — жизни и неуязвимость, Шури — шансы монет, Боргард — хлыст), сила одного забега (благословения), power-neutral сайдгрейд на ровно один забег, временные дропы, и — отдельно — **подмена эффекта, а не числа**: тип молитвы у Йенны и тип основного оружия у Присциллы на той же кнопке. Если стек начнёт знать про «благословение», «королеву» или «тюрьму», каждая новая система будет править его код, а правила вроде «сайдгрейд не даёт силы» окажутся размазаны по ветвлениям. Решение нужно сейчас: GDD Модификаторов — первый в порядке проектирования, и его нельзя писать без контракта.

### Constraints
- Технические: ~300 врагов + ~500 снарядов на GameObject без DOTS, бюджет 0 GC/кадр (`systems-index.md`, Шина событий); p95 ≤ 16,6 мс ещё не доказан (ADR-0002, спайк) — стек не должен отнимать заметную долю кадра.
- Coding standards: игровые значения — в данных, DI вместо синглтонов, публичные методы тестируемы юнит-тестами, детерминизм тестов.
- Сроки: команда 4+, оценка 12–16+ мес. при цели 5–7 — контракт должен быть маленьким и не требовать редакторских инструментов сверх инспектора `ScriptableObject`.
- Совместимость: полная и цензурная сборки совместимы только через ID (`systems-index.md`, Сохранения).

### Requirements
- Хранить числа по ID и слоты эффектов по ID; **ничего не знать об источниках**.
- Поддержать сроки жизни: навсегда (прокачка) и один забег (благословения, сайдгрейд, выбор оружия перед забегом); временные эффекты дропов — за счёт системы-владельца.
- Подмена эффекта (молитва, оружие) — через слоты, без комбинаторики с сайдгрейдом (CD-SYSTEMS).
- Детерминированный результат при одинаковом наборе и порядке источников (тесты, RNG с seed).
- 0 аллокаций в чтении и в изменении источников во время забега.
- Числа баланса — в данных, формулы — здесь, значения — в GDD.
- Дать данные для проверки power-neutral сайдгрейда. **Критерий нейтральности задаёт GDD 49 «Сайдгрейды»** (совместно с GDD экономики), а не этот ADR; стек даёт только `powerWeight` у `StatDefinition` (вес «силы» единицы стата, задаётся в данных) — по нему Валидатор и тесты считают суммарный силовой вклад набора записей.

## Decision

Вводится **один стек модификаторов на владельца** (`ModifierStack`, обычный C#-класс, не `MonoBehaviour`). В MVP владелец один — Чемпион; враги и боссы стек не используют (их сложность фиксирована данными, масштабирование Вагитты берётся из кэша силы Контекста забега). Стек — **производное состояние**: он никогда не сериализуется. После загрузки восстанавливаются **только `Permanent`-источники** — каждая система-владелец переоткрывает свои из своего сохранённого состояния (Прокачка у королев — из купленных уровней). `Run`-источники после загрузки **не восстанавливаются**: сохранение посреди забега не входит в бюджет первого релиза (`game-concept.md`, Key Technical Challenges), поэтому загрузка всегда происходит вне забега, где `Run`-записей нет. Исключение — то, что игрок уже выбрал *для следующего* забега (сайдгрейд, оружие Присциллы): это состояние сохраняют Сайдгрейды и Контекст забега, а `Run`-handle открывают только при старте забега (см. «Граница забега»).

**Числа.** Каждый стат описан в каталоге (`StatDefinition`: строковый ID, базовое значение, min, max, необязательный `multiplierCap`, `powerWeight`, режим округления — `None` / `Floor` / `Round` для счётных величин вроде жизней и зарядов). **«Категория» из `game-concept.md` («аддитивно внутри категорий (стилеты / хлыст / молитва / живучесть)») — это и есть `StatId`**: второго понятия группировки в стеке нет. Значение собирается по формуле:

```
mult  = (1 + Σ PctAdd) × Π (1 + More_i)
mult  = min(mult, multiplierCap)          // если multiplierCap задан; иначе без потолка
raw   = (base + Σ Flat) × mult
value = clamp(round(raw), min, max)      // round = MidpointRounding.AwayFromZero, явно
если есть Override-записи: value = clamp(round(Override с наибольшим priority), min, max)
         при равном priority побеждает запись с большим sequence (позже добавленная) —
         это только защитный фолбэк: равный priority у Override, как и у слотов, — ошибка данных
```

Три слоя выбраны намеренно: сумма процентов (`PctAdd`) сдерживает разгон — двадцать благословений «+10%» дают +200%, а не ×6,7, что поддерживает правило «ширина выбора, а не мощь»; `More` — редкий, явно отмеченный в данных множитель; `Override` — для жёстких правил («ровно 1 жизнь» в гэг-сайдгрейде), а не для баланса. `multiplierCap` — тот самый «общий потолок суммарного множителя», значение которого концепт отдаёт GDD: он ограничивает именно разгон от модификаторов, а `max` — абсолютную границу величины (например, «не больше 6 жизней» независимо от базы). Одного `max` недостаточно: при росте `base` через прокачку `max` пришлось бы пересчитывать вручную, а потолок множителя от базы не зависит.

**Слоты эффектов.** Слот (`SlotDefinition`: строковый ID, эффект по умолчанию) хранит одну запись-победителя. Запись слота несёт `EffectId` и `priority` из данных; побеждает наибольший `priority`, при равенстве — больший `sequence`. Стек **не исполняет** эффекты: он отдаёт индекс эффекта, а потребитель (Оружие, Молитва) сопоставляет его со своей реализацией. Равные приоритеты в одном слоте у источников, которые могут сосуществовать, — ошибка данных, которую ловит Валидатор контента.

**Источники.** Источник открывает handle с указанием срока жизни и добавляет в него записи; закрытие handle снимает все его записи разом. Стек хранит только handle, срок жизни, записи и (только в dev-сборках) отладочную метку для телеметрии — ни типа источника, ни ссылки на него. Метка задаётся отдельным `void`-методом с `[Conditional]`, а не параметром `Open`: так сигнатура интерфейса одинакова во всех сборках, а вызов вместе с вычислением аргумента исчезает из релиза. Значение `0` у handle и индексов зарезервировано как «невалидное» (`Generation` начинается с 1, индексы хранятся как `index + 1`), поэтому неинициализированное поле `default(...)` не может молча попасть в чужой источник или в стат №0. Сроки жизни: `Permanent`, `Run`. Срок `Segment` намеренно **не вводится**: в концепте у него нет потребителя (благословения живут весь забег); если GDD Структуры забега его потребует, он добавляется отдельной правкой этого ADR.

**Граница забега.** У массовой очистки один владелец — **Структура забега**. Порядок фиксирован:

```
конец забега (победа / поражение / «Явка с повинной»)
  → Структура забега: ClearLifetime(Run)          // благословения, сила этого забега
  → тюрьма / лагерь                               // Сайдгрейды и Контекст забега только ЗАПОМИНАЮТ
                                                  // выбор для следующего забега, handle не открывают
  → старт следующего забега
  → Контекст забега открывает Run-handle: оружие Присциллы, затем Сайдгрейды — свой
  → первый сегмент
```

Так `ClearLifetime(Run)` не может стереть сайдгрейд или выбор оружия: их записи появляются в стеке после очистки. Таймерные эффекты (неуязвимость из дропа) стек не тикает: система-владелец закрывает свой handle сама по Времени и паузе.

**ID.** Стабильные строковые ID живут в каталоге `ModifierCatalog` (`ScriptableObject`, часть Данных контента, **иммутабелен в рантайме**). Таблицу плотных `int`-индексов (`StatIndex`, `SlotIndex`, `EffectIndex`) строит композиционный корень каждую игровую сессию в отдельном C#-объекте, а не в полях `ScriptableObject` и не в `static` — иначе при Enter Play Mode без Domain Reload индексы переживут сессию. Рантайм работает только с индексами. Наружу (сохранения, телеметрия, цензурная сборка) уходят только строки.

**Чтение.** Pull: `Get(StatIndex)` возвращает кэш; при изменении записей стат помечается dirty и пересчитывается при следующем чтении. Глобальный счётчик `Version` растёт при каждом изменении — потребитель, кэширующий производные значения (например, HUD или скорость перезарядки), сравнивает версию, а не подписывается. Событий стек не публикует.

### Key Interfaces

```csharp
/// <summary>Плотный рантайм-индекс стата. Хранится как index + 1: default(StatIndex) невалиден.</summary>
public readonly struct StatIndex
{
    internal readonly int Raw;                       // 0 = невалидный
    internal StatIndex(int index) { Raw = index + 1; }
    public bool IsValid => Raw != 0;
    internal int Index => Raw - 1;
}
// SlotIndex и EffectIndex — та же форма (Raw, internal ctor, IsValid).

/// <summary>Непрозрачный handle источника. Generation начинается с 1; default(handle) невалиден,
/// handle после Close детектируется по несовпадению Generation.</summary>
public readonly struct ModifierSourceHandle
{
    internal readonly int Id;
    internal readonly int Generation;                // 0 = невалидный
    internal ModifierSourceHandle(int id, int generation) { Id = id; Generation = generation; }
    public bool IsValid => Generation != 0;
}

public enum ModifierLifetime { Permanent, Run }
public enum StatOp { Flat, PctAdd, More, Override }

/// <summary>Чтение для потребителей. Без аллокаций.</summary>
public interface IModifierReader
{
    /// <summary>Итоговое значение стата по формуле ADR-0007.</summary>
    float Get(StatIndex stat);
    /// <summary>Победитель слота или эффект по умолчанию.</summary>
    EffectIndex GetSlot(SlotIndex slot);
    /// <summary>Растёт при любом изменении записей.</summary>
    int Version { get; }
}

/// <summary>Запись для источников. Источник владеет своим handle.</summary>
public interface IModifierWriter
{
    ModifierSourceHandle Open(ModifierLifetime lifetime);
    void AddStat(ModifierSourceHandle source, StatIndex stat, StatOp op, float value, int priority = 0); // priority — только для Override
    void SetSlot(ModifierSourceHandle source, SlotIndex slot, EffectIndex effect, int priority);
    void Close(ModifierSourceHandle source);
    void ClearLifetime(ModifierLifetime lifetime); // Permanent не очищается этим вызовом
}

/// <summary>Отладочные метки источников; вызов и вычисление аргумента вырезаются из релиза.
/// Условие вычисляется по define-ам сборки ВЫЗЫВАЮЩЕГО.</summary>
public static class ModifierDebug
{
    [System.Diagnostics.Conditional("DEVELOPMENT_BUILD"), System.Diagnostics.Conditional("UNITY_EDITOR")]
    public static void SetDebugLabel(IModifierWriter writer, ModifierSourceHandle source, string label)
        => (writer as IModifierDebugSink)?.SetLabel(source, label);
}
internal interface IModifierDebugSink { void SetLabel(ModifierSourceHandle source, string label); }

/// <summary>Каталог ID (часть Данных контента). Строки — только на загрузке и на границах (сохранения, телеметрия).</summary>
public interface IModifierCatalog
{
    bool TryGetStat(string id, out StatIndex index);
    bool TryGetSlot(string id, out SlotIndex index);
    bool TryGetEffect(string id, out EffectIndex index);
    string GetStatId(StatIndex index);
    string GetEffectId(EffectIndex index);
}
```

### Implementation Guidelines
- Стек **must never** содержать типы, перечисления или ветвления, называющие источник (благословение, королева, тюрьма, сайдгрейд, дроп). Новая система-источник **must not** требовать правки кода стека.
- Стек **must never** исполнять эффект — он только разрешает слот в `EffectIndex`.
- Стек **must never** сериализоваться; системы-владельцы `Permanent`-источников **must** восстанавливать свои handle после загрузки из своего сохранённого состояния; `Run`-источники после загрузки **must not** восстанавливаться (загрузка всегда вне забега).
- Потребители **must** получать `IModifierReader`, источники — `IModifierWriter` через конструктор/инициализацию от композиционного корня (Поток игры). Статический доступ и синглтон стека **forbidden**.
- Чтение и изменение во время забега **must** выделять 0 байт: предвыделенные массивы по размеру каталога и пул записей; без LINQ, boxing, замыканий, `string` в горячем пути. Отладочная метка **must** задаваться только через `[Conditional]`-метод `ModifierDebug.SetDebugLabel`; параметры, меняющие сигнатуру между dev и release (`#if` вокруг параметра), **forbidden**.
- Пересчёт стата **must** обходить записи в порядке `sequence`, чтобы результат float был детерминирован при одинаковом порядке источников.
- Числа баланса (base, min, max, значения модификаторов, priority) **must** лежать в `ScriptableObject`-данных; в коде **forbidden** любые числа баланса.
- Таймерные эффекты **must** закрываться системой-владельцем по Времени и паузе; стек не знает о времени.
- `ClearLifetime(Run)` **must** вызываться только Структурой забега, ровно один раз — в конце забега, до тюрьмы/лагеря; другие системы **must not** вызывать массовую очистку.
- Системы, готовящие следующий забег (Сайдгрейды, Контекст забега), **must** открывать свои `Run`-handle только при старте забега, никогда — в тюрьме или лагере.
- Использование `default`-handle, `default`-индекса или handle после `Close` **must** детектироваться (`IsValid` / `Generation`: assert в dev, no-op в релизе).
- `static`-изменяемое состояние в сборке стека **forbidden**; каталог `ScriptableObject` **must** быть иммутабелен в рантайме, таблица индексов **must** строиться композиционным корнем каждую сессию.
- Округление **must** указывать `MidpointRounding` явно (`Math.Round(x, MidpointRounding.AwayFromZero)`); `Mathf.Round` для счётных статов **forbidden** (банковское округление .5).
- Рефлексия в рантайм-сборке стека **forbidden** (IL2CPP stripping; `link.xml` не нужен); допустима только в тестовой сборке.
- Раскладка сборок **must** быть: `Game.Modifiers` (стек, интерфейсы, структуры; `noEngineReferences: true`), `Game.Modifiers.Data` (каталог на `ScriptableObject`), тесты — `Assets/Tests/EditMode/Modifiers/`. Сборки систем-источников ссылаются на `Game.Modifiers`, но не наоборот.
- Power-neutral сайдгрейда — правило данных (критерий — GDD 49, вес — `powerWeight`), проверяемое Валидатором контента и тестом каталога, **not** ветвление в стеке; стек `powerWeight` не читает.
- Данные источников со сроком `Run`, **кроме выбора оружия в Контексте забега**, **must not** ссылаться на слоты основного оружия и молитвы (ограничение CD-SYSTEMS «без комбинаторики с сайдгрейдом»). Типы молитвы задаёт только `Permanent`-источник Прокачки (Йенна). Проверка — тест каталога, затем Валидатор контента.

## Alternatives Considered

### Alternative 1: Общий стек с источниками-handle (выбрано)
- **Description**: описано в Decision.
- **Pros**: одна формула для всех; новый источник — данные плюс несколько вызовов `Open/Add/Close`; стек тестируется изолированно в EditMode; 0 GC достижим предвыделением.
- **Cons**: формула общая — частные исключения приходится выражать через `Override`/`More`, а не кодом; отладка «откуда взялось число» требует dev-меток.
- **Rejection Reason**: —

### Alternative 2: Модификаторы внутри каждой системы
- **Description**: Оружие, Здоровье, Дропы и т. д. хранят свои бонусы и сами решают, как их складывать; источники пишут напрямую в нужную систему.
- **Pros**: нет общего узкого места; каждая система проста по отдельности.
- **Cons**: источники (благословения, сайдгрейд) должны знать всех потребителей — это тот же God Object, только у источника; формулы стакания расходятся между системами, и правило «ширина, а не мощь» проверить нельзя; очистка на границе забега размазана по восьми местам.
- **Rejection Reason**: связность N×M вместо N+M; кроме того, без общей формулы и общего `powerWeight` проверка power-neutral (критерий — GDD 49) пришлось бы писать отдельно под каждую систему.

### Alternative 3: Система по образцу GAS (атрибуты + эффекты с тегами и длительностями)
- **Description**: атрибуты, эффекты с тегами, длительностями, стаками и условиями применения; стек тикает время и проверяет теги.
- **Pros**: выразительно; покрывает будущие сложные взаимодействия.
- **Cons**: на порядок больше кода и данных; теги и условия — путь к «билдам-таблицам», которые концепт явно запрещает (CD-SYSTEMS); тиканье длительностей связывает Foundation-систему со Временем и паузой; дорого для команды 4+ при сроках 12–16+ мес.
- **Rejection Reason**: сложность не окупается — механики игры требуют только чисел, двух сроков жизни и подмены эффекта.

### Alternative 4: Push-события об изменениях на Шину событий
- **Description**: стек публикует `StatChanged`, потребители держат копии значений.
- **Pros**: потребители не опрашивают стек.
- **Cons**: зависимость от ещё не зафиксированного контракта шины; лавина событий при массовой очистке на границе забега; копии рассинхронизируются.
- **Rejection Reason**: pull из кэша с `Version` дешевле и не требует подписок (выбор пользователя).

## Consequences

### Positive
- Риск God Object из `systems-index.md` закрыт структурно: стек не может знать источники, потому что его API их не принимает.
- Правило «ширина выбора, а не мощь» получает математическую опору — аддитивные проценты не разгоняются экспоненциально.
- Подмена молитвы и оружия Присциллы — одна строка данных (`SetSlot`) без ветвлений в потребителе.
- Стек не участвует в сохранениях — ADR-0005 не нужно описывать его схему, совместимость полной и цензурной сборок не затронута.
- Детерминизм и чистый C# дают дешёвые EditMode-тесты.

### Negative
- Формула одна на всех: гейм-дизайнеру придётся выражать редкие «особые» правила через `More` и `Override`, а сами эти слои — держать редкими (дисциплина данных).
- Отладка происхождения чисел в релизе невозможна (метки вырезаны) — только в dev-сборках.
- Каталог ID становится частью Данных контента: переименование строкового ID ломает ссылки в данных и сохранениях систем-источников.
- Системы-владельцы `Permanent`-источников обязаны сами восстанавливать свои handle после загрузки — эта обязанность распределена, и её легко забыть.
- Решение опирается на отсутствие сохранения посреди забега; если ADR-0005 его введёт, восстановление `Run`-источников придётся спроектировать заново.

## Risks
- **Забытый `Close`** (источник уничтожен, handle остался) → бонус «течёт» в следующий забег. *Митигация:* срок жизни `Run` очищается массово; для `Permanent` — тест «загрузка → пересоздание → значения совпадают»; dev-счётчик открытых handle в телеметрии.
- **Конфликт равных приоритетов в слоте** → победитель зависит от порядка инициализации. *Митигация:* тест каталога сейчас, правило Валидатора контента позже; dev-assert при равенстве priority у разных источников.
- **Дрейф `More`/`Override` в балансе** → разгон силы. *Митигация:* `multiplierCap`; тест каталога (позже Валидатор) считает долю `More`/`Override`; balance-check по формуле из этого ADR.
- **Защиты на Валидаторе приходят поздно** (в `systems-index.md` он после диалогов и сцен). *Митигация:* тест каталога из Validation Criteria с первого спринта.
- **Недостижение 0 GC** из-за `string` или `params` в API. *Митигация:* строки — только в каталоге на загрузке; Profiler-проверка из Engine Compatibility — критерий приёмки.
- **Восстановление после загрузки в другом порядке** (Контекст забега до Прокачки) меняет `sequence`. Для чисел порядок не важен (суммы/произведения, с точностью до float-epsilon); для слотов и `Override` победитель зависит только от priority **при условии**, что равные priority запрещены. *Митигация:* правило Валидатора контента «равный priority в одном слоте или у `Override` одного стата — ошибка» и dev-assert; тест «восстановление в обратном порядке → те же победители».
- **Расхождение float между Mono и IL2CPP.** *Митигация:* тесты сравнивают с epsilon; счётные статы округляются явно (`AwayFromZero`), поэтому дискретные значения совпадают.
- **Enter Play Mode без Domain Reload** оставляет `static`/кэш `ScriptableObject` от прошлой сессии. *Митигация:* запрет `static`-состояния и иммутабельный каталог (Implementation Guidelines); источник знаний — NOT SOURCEABLE в `docs/engine-reference/unity/`.
- **Риск источника знаний:** домен Core/Scripting не покрыт справочником движка (NOT SOURCEABLE); решение опирается только на `ScriptableObject` и чистый C#, которые не менялись на границах 6.x по данным `breaking-changes.md` — подтвердить проверками из Engine Compatibility.

## Performance Implications
- **CPU**: чтение — O(1) из кэша; пересчёт стата — O(k) по его записям (ожидаемо k < 30: ~30–40 благословений в пуле, но за забег берётся 5–6) только после изменения; изменения редки (выбор благословения, подбор дропа, граница забега). Ожидаемо ≪ 0,05 мс/кадр — подтвердить на спайке ADR-0002.
- **Memory**: массивы по размеру каталога (десятки статов и слотов) плюс пул записей ~ сотни элементов — единицы КБ.
- **Load Time**: построение индексов каталога при загрузке — один проход по строкам, пренебрежимо.
- **Network**: N/A (одиночная игра).

## Migration Plan
Кода нет (основного Unity-проекта ещё нет) — миграция не требуется. Концепт-прототип выбрасывается и на этот контракт не переводится.

## Validation Criteria
- EditMode-тесты: формула (каждый слой отдельно и вместе, clamp, округление .5 → от нуля, override с равным priority — assert), `default`-handle и `default`-индекс — assert/no-op, восстановление в обратном порядке → те же победители слотов, слоты (priority, sequence, default), `Close` снимает все записи, `ClearLifetime(Run)` не трогает `Permanent`, использование закрытого handle детектируется, детерминизм при одинаковом порядке, независимость числа от порядка источников с точностью до float-эпсилон.
- Тест восстановления: сохранённые уровни прокачки → пересоздание стека → те же значения.
- Тест границы забега: сайдгрейд и оружие, выбранные в тюрьме/лагере, присутствуют в стеке в первом сегменте следующего забега; благословения прошлого забега — нет.
- **Тест каталога (временная замена Валидатора контента)** — EditMode-тест загружает `ModifierCatalog` и все данные источников и проверяет: нет равных priority в одном слоте и у `Override` одного стата; доля `More`/`Override` не превышает порог из данных; `Run`-данные, кроме выбора оружия, не ссылаются на слоты оружия и молитвы; суммарный `powerWeight` каждого сайдгрейда в пределах критерия GDD 49. Работает с первого спринта; когда появится Валидатор контента, правила переходят в него, а тест остаётся регрессионным.
- Profiler: 0 B GC за кадр в синтетическом забеге с открытием/закрытием источников.
- Архитектурный тест (`Assembly.GetReferencedAssemblies()` в тестовой сборке): `Game.Modifiers` не ссылается ни на `UnityEngine`, ни на сборки систем-источников; `noEngineReferences` дополнительно проверяет это компилятором.
- После GDD Модификаторов: каждый модификатор из GDD выражается без правки кода стека.
